# 下位机镜像摘要兼容修复方案

## 问题与目标

安装包 `0.3.0-master-ci-20261009-46283f6-linux-x64` 的 config 摘要为 `2f1ce15d…`，引用它的 OCI manifest 摘要为 `7177f976…`。目标容器已使用后者，旧逻辑直接比较两者导致“构建不一致”。本次统一以镜像 config 的原始字节 SHA256 作为运行构建身份；只有验证关联后才能将其他类型摘要转换为 config 摘要。

## 范围与接口

- 上位机保持前端接口及 DTO 不变：运行查询的 `image_id` 返回规范化的 config 摘要，安装前跳过判断、检查最新构建、安装后确认共用后端运行查询。
- 经典 Docker 存储使用已有 config ID。containerd 存储识别镜像 descriptor，对容器实际引用的不可变镜像 ID 导出归档，以只读、流式方式验证 manifest/index 与 config 的关联，不写入镜像层文件。
- 仅缓存经过验证的不可变摘要到 config 摘要的映射；缓存命中仍重新查询容器是否存在、运行状态及实际镜像引用。tag 不作为映射键，不能用当前 tag 推断历史容器身份。
- 缺失 Python、导出失败、摘要错误、平台歧义或关联无法证明时返回中文查询错误，不放宽为校验通过。保持整次查询的总超时，并清理子进程。
- 下位机安装器兼容经典 `<摘要>.json` 和 `blobs/sha256/<摘要>` 配置路径，校验配置内容；只有 OCI manifest 的内容摘要及 config 关联都正确时，才能接受本机返回的对应 manifest ID。加载后再次核对身份，容器创建失败应返回非零。
- 发布清单继续使用 schema 1 的 `image_id` 字段，但从镜像归档计算 config SHA256，不依赖构建机器的 `docker image inspect .Id` 含义；兼容既有清单读取方。
- 本次不编辑既有历史安装包清理功能，不连接设备、不部署、不重启模块或容器。

## 测试与验收

先增加失败测试，再实现。覆盖经典 Docker config ID、OCI manifest 引用同一 config、错误摘要及错误关联、多平台歧义、无容器/停止容器、导出失败与超时。安装器使用临时目录和 mock Docker 测试路径兼容、相同镜像跳过加载、错误镜像更新、加载与容器创建失败。清单生成器测试两种归档格式、配置内容摘要、错误配置及多镜像拒绝。

在本机执行 Python 行为回归、Node 工作流测试、前端静态检查及构建、相关 Rust 单测。编译环境不支持的检查如实记录；远端编译、联调及部署不在此次授权范围内。
