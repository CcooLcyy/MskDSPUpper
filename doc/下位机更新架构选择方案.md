# 下位机更新架构选择方案

## 目标与范围

软件更新的下位机更新页增加目标架构选择：ARM64（默认）和 x64。只修改上位机更新流程，不修改下位机发布链、不自动连接或部署目标设备。

## 接口与行为

- 平台标识分别为 `linux-arm64` 和 `linux-x64`，Docker 对应 `linux/arm64` 与 `linux/amd64`。
- ARM64 保持 `mskdsp-lower` 更新源，支持 `stable`、`beta`、`ci`；x64 使用独立 `mskdsp-lower-x64` 更新源，目前仅支持 `ci`。选择 x64 自动切换到 CI，并在页面说明通道限制。
- 检查更新和读取缓存接口增加可选 `platform` 参数；省略时保持 ARM64，兼容既有调用。清单平台必须匹配请求平台；不支持的平台、平台与通道组合返回中文错误。
- 前端源配置保留 `VITE_LOWER_UPDATE_STATIC_BASE_URL`，新增 `VITE_LOWER_UPDATE_X64_STATIC_BASE_URL`，分别覆盖两个架构的源；空配置回退各自公开源。
- 缓存仍按通道/平台分目录。前端自动状态、下载任务互斥与检查任务按平台和通道隔离；默认检查 ARM64 三个通道，切换 x64 后检查 x64 CI。旧任务可完成，但不得覆盖当前架构状态。后端继续使用原有缓存目录锁保护下载落盘和清理。
- 架构选择保存在全局 Provider 当前会话中，跨页面保留，应用重新启动默认 ARM64。正在手动检查、下载或部署时禁止切换；其他通道的后台任务可继续完成。
- 切换架构清空页面清单、下载、上传、安装和镜像校验状态，重新读取所选架构缓存；异步缓存结果必须忽略过期请求。只允许下发与所选架构和通道一致的包。
- 离开页面后，不允许残留的预检结果或确认弹窗继续发起上传、安装；已经发出的 SSH 命令可以正常结束。
- 上传及安装命令沿用既有流程，继续以目标容器镜像 ID 校验安装结果。

## 验收与异常

- 无平台参数的旧调用仍使用 ARM64；x64 检查使用独立源并接受 `linux-x64` 清单。
- 不同架构缓存与下载任务互不污染，切换后不会展示或下发旧架构包；返回原架构可复用其有效缓存。
- 错误平台清单、未知架构及 x64 非 CI 请求被拒绝；缺失清单或网络异常显示现有中文失败信息。
- 通过 Node 工作流测试验证平台/通道/源映射和前端接线，Rust 单测验证后端清单校验与缓存隔离；执行前端构建及 lint，并在本地工具可用时执行相关 Rust 单测。

## 验证记录

- `npm run test:workflow`：292 项通过，包含实际执行 Provider 的架构切换与旧任务完成隔离测试，以及页面卸载后的部署入口约束检查。
- `npm run test:offline`：74 项通过；`npm run lint`、`npm run build` 通过。
- 下位机更新 Rust 定向单测：31 项通过。Windows 的 `protoc` 无法识别当前中文仓库路径，通过临时英文目录 Junction 指向同一工作区执行 Cargo 测试；没有修改构建脚本。
- 本地浏览器预览因连接失败未完成视觉验证；未连接、安装或更新远端服务器及真机。
